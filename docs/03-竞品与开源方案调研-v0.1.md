## 0. 结论先行

**一、市场侧：同款玩法没有，但有大量"相邻但不同"的产品。** 现有产品分三类——模板式（把你的脸放进预设场景）、贴纸式（画个小人贴上去）、换脸式（替换照片里已有的人）。**没有一款在做"固定角色 + 你的原照片 + 写实光影 + 位置推理"这件事。** 这是空位，但空位小，需要靠验证确认它值不值得填。

**二、技术侧：有一个"教科书级"的开源项目，但它的许可只覆盖一半。** `bcmi/libcom` 把图像合成拆成六个子任务（位置评估、光照协调、阴影生成、反射生成、生成式合成、质量评分），每个子任务都挂了一个 SOTA 实现，仓库 Apache 2.0、**至今活跃**（2026-10-05 仍有提交）。其中 `KontextBlendingHarmonizationModel` 的功能描述几乎逐字就是我们 PRD 的话。

**但必须分清"代码许可"与"权重许可"**：该模块 README 第 66 行注明 based on FluxKontext，而 FLUX.1 Kontext [dev] 的权重是 **FLUX.1-dev Non-Commercial License（非商用）**。libcom 的 Apache-2.0 治不了它调起来的那个权重。同理 `OSInsertModel` 对应的 `bcmi/OSInsert-Image-Composition` **仓库无 LICENSE**。**结论：libcom 的两个生成式合成模块都不能商用；能安全商用的是它的判别式评分模型（OPA / HarmonyScore / FOSScore）。** 详见 2.1 与第 4 节。

**三、有一个现成的原型骨架可以借鉴思路，但不能抄代码。** `haoyang504/Anime_In_Real_Life` 是"动漫角色融入实景照片"的 Web 应用，双模式架构（浏览器本地抠图贴图 + Nano Banana Pro 光影融合）与我们需求的结构完全一致。但其**根目录无 LICENSE 文件（GitHub 许可字段为空，0 星）**——无许可证默认保留所有权利，只能读思路、不能复制文件。

**四、v0.1 方案要改四处**（详见第 6 节）：加入自动评分排序、重新评估自建开源模型的经济性、把 AnyDoor 从"可用"降级为"仅借鉴"、**把 libcom 的定位从"整体可用的工具箱"收窄为"只用它的评分模型"**。

## 1. 市场侧：同类产品地图

### 1.1 模板式（主流路线，与我们最容易混淆）

| 产品 | 平台 | 玩法 | 与我们的差别 |
|------|------|------|--------------|
| 秒画趣拍（商汤） | 微信小程序 | 上传 1 张照片 + 选模板，生成校园毕业照、创意合照、二次元、新国风等风格写真。官方称采用多特征渐进式融合训练保证人物一致性 | **模板决定场景，你的脸进去**。我们是相反方向：**场景是你的照片，角色是固定的** |
| 妙鸭相机（阿里） | App / 小程序 | 上传 10 至 20 张自拍构建数字分身，9.9 元起生成写真；支持与虚拟偶像、明星模板合成"打破次元壁的互动合影" | 同上。且需要多张照片建模，门槛高于单张 |
| 可拍 | Android App | 单张照片转为日漫、赛博朋克等风格，与授权模特模板换脸 | 模板授权模式，本质是换脸 |

**需求规模的证据**：秒画趣拍试运营第 9 天，日活突破 52 万，用户总量 146 万，日 PV 4117 万。这说明"把我的照片变得特别"是一个被验证过的巨大需求。但注意——**这是模板式的胜利，不是我们的路线的胜利。**

### 1.2 贴纸式（交互最接近，但质感不同）

| 产品 | 平台 | 玩法 | 与我们的差别 |
|------|------|------|--------------|
| emoji 小人 | 微信小程序 | 上传照片 → 生成保留动作、表情、发型、服饰细节的 emoji 风格小人 → **在小程序里拖拽调整位置和大小 → 一键合成**。按张收费，评分 3.6 | 交互几乎一致，但**不融合光影**，是贴纸质感。且它贴的是"你自己"的小人，不是固定角色 |

**真实用户差评（非常有价值，提前避坑）**：

- "多人合照基本没成"——多人场景是坑，我们已在 PRD 里排除
- "iOS Emoji 就不太稳定了，同一组照片换个角度，头发直接变成一团，抠图边缘偶尔还会露白"——**抠图边缘发白**是我们一定会遇到的问题（设定图白底）
- "我生成一张差不多等了两三分钟"——**生成耗时是用户可感知的痛点**，我们预估的 60 秒优于它，但仍需进度反馈
- "按张收费有点顶，换个风格就得再付一次"——按张计费会被骂，**建议按次（一组 4 张）计费**

### 1.3 换脸式（不是同一件事）

| 产品 | 平台 | 玩法 | 与我们的差别 |
|------|------|------|--------------|
| 合照生成器 | 微信小程序 | 上传背景图 → 涂抹掉要替换的人像 → 上传单人照 → 合成 | 它需要**先有一个人**才能换。我们是**新增一个不存在的人**，且要她站得住 |

### 1.4 替代方案（用户不用我们时会怎么做）

| 替代路径 | 门槛 | 效果 | 谁在用 |
|----------|------|------|--------|
| 用 ComfyUI 自己搭工作流 | 高（要 GPU、要装节点） | 可控性最强 | 技术型爱好者 |
| 用即梦 / Nano Banana 手写提示词 | 中（要会写提示词） | 效果上限高但不稳定 | 小红书上的教程党 |
| 用 PS 手动合成 + 调色 | 高 | 可控但慢 | 少数人 |
| 找画师约图 | 成本高、周期长 | 质量最高 | 有付费意愿的核心粉 |

**结论**：替代方案的共同问题是"要么门槛高、要么不稳定"。**把这件事降到"传张图、拖个框、点生成"就是产品价值所在。**

### 1.5 市场空位判断

把三类产品放在一个二维坐标上：横轴是「场景来源」（预设模板 ← → 用户自己的照片），纵轴是「角色来源」（用户自己 ← → 固定虚拟角色）。

- 模板式产品占据「预设模板 + 用户自己」（左上）
- 贴纸式产品占据「用户照片 + 用户自己」（左下）
- **「用户照片 + 固定虚拟角色」这一格（右下）基本是空的**

这一格空着的原因也很清楚：它同时要求**角色一致性**（固定角色不能画崩）和**场景融合**（位置、光影、遮挡都要对），两个难点叠加。模板式只需解决第一个，贴纸式只需解决第二个。

**这个空位值不值得填，取决于 Step 1 的实测成功率。** 如果写实融合的成功率只有 35%，这一格事实上是"技术还不允许"，而不是"没人想到"。

## 2. 技术侧：开源项目地图

### 2.1 核心发现：libcom（整个领域的工具箱）

| 项 | 内容 |
|----|------|
| 地址 | github.com/bcmi/libcom |
| 机构 | 上海交大 BCMI Lab（Li Niu 团队） |
| 仓库许可 | **Apache 2.0**（741 星，2026-10-05 仍在提交，已发布 PyPI 包） |
| **权重许可（关键）** | **仓库许可不等于模块可用。** 两个生成式合成模块分别依赖非商用权重与无许可仓库：<br>`KontextBlendingHarmonizationModel` → FluxKontext → **FLUX.1 Kontext [dev] 权重为 FLUX.1-dev Non-Commercial License**（依据 black-forest-labs/flux README 模型表第 47 行）<br>`OSInsertModel` → `bcmi/OSInsert-Image-Composition` → **仓库无 LICENSE，基座模型许可未在仓库层面声明**（双重待核实） |
| **可安全商用的部分** | `OPAScoreModel`、`HarmonyScoreModel`、`FOSScoreModel` 均为**判别式模型**，不依赖 Kontext 权重，无生成权重牵连 |
| 形态 | `pip install libcom`，提供在线工作台 libcom.ustcnewly.com |

**一句话定位（已修正）：用 libcom 的评分模型，不用它的合成模型。**

它把我们需要的每一个环节都做成了独立模块。**这是本项目最重要的一份参考资料，但引用时必须区分"能看"和"能用"。**

| libcom 模块 | 解决我们哪个环节 | 对我们的价值 | 商用可用性 |
|-------------|------------------|--------------|-----------|
| **KontextBlendingHarmonizationModel**（基于 Flux Kontext） | 把前景插入背景的指定边界框内，姿态视角不变；harmonization 模式自动调整前景光照 | 功能描述与我们的核心需求几乎逐字对应 | **不可商用**（依赖 FLUX.1-dev 非商用权重）。可用来验证"这条路的上限长什么样"，但不能进产品 |
| **OSInsertModel**（OSInsert） | 同上，分 conservative / aggressive 两档，可调整前景姿态视角；支持前景形状 mask | 解决"倚靠""坐着"需要改姿态的场景 | **不可商用 / 待核实**（对应仓库无 LICENSE） |
| **FOPAHeatMapModel**（FOPA） | 给定背景与前景，**预测所有位置与尺度的合理性得分图**，输出最优位置与尺度 | 直接解决"位置合理"，还能替代用户手动标注的一半工作 | 可用（判别式） |
| **OPAScoreModel**（OPA） | 评估合成图中前景的**位置与尺度是否合理** | 可做自动评分排序 | **可用（判别式），推荐** |
| **ShadowGenerationModel**（GPSDiffusion） | 为插入的物体生成合理阴影 | 直接解决接触阴影 | 可用（MIT） |
| **HarmonyScoreModel**（BargainNet） | 评估前景与背景的**光照和谐程度** | 可做自动评分排序 | **可用（判别式），推荐** |
| **FOSScoreModel**（DiscoFOS） | 评估前景与背景的**几何与语义兼容性** | 可做自动评分排序 | **可用（判别式），推荐** |
| **PainterlyHarmonizationModel**（PHDNet / PHDiffusion） | **艺术风格背景 + 写实前景**的协调 | 如果后续做贴纸风或二次元场景，这是对口模块 | 待逐个核实权重 |
| **ReflectionGenerationModel**（RGDiffusion） | 为插入物体生成反射 | 桌面、湿地、玻璃场景会用到 | 待逐个核实权重 |
| ImageHarmonizationModel（PCTNet / LBM） | 传统光照协调 | 轻量替代方案 | 待逐个核实权重 |
| 在线工作台 | libcom.ustcnewly.com | 可直接上手试效果，**不用写代码就能验证我们这条链路的上限** | 验证用途，不受商用许可约束 |

**最实用的用法（已调整）**：在写任何代码之前，先去 libcom 的在线工作台，用你自己的照片和设定图手工跑一遍"插入 + 打光 + 阴影"，**看效果上限**。这一步的价值是"判断天花板"，不是"选型"——因为 Kontext 模块本身进不了商用产品。

## 3. 推荐架构（已被 05 号文档推翻并重写）

> **本节原为「三层线性递进：纯 API → API+评分 → 自建开源栈」，经架构师复核后判定为错误切法，已被 05 号文档第 6 节的「单一骨架 + 可插拔生成器」取代。**
>
> 原切法的错误在于：Qwen-Image-Edit-2511 的权重是 Apache-2.0 且可下载，**API 与自建跑的是同一个模型**。把它当两条路线，等于为同一个模型写两套代码、维护两套提示词资产、做两次不可控的跨期对照。
>
> 正确切法：**从第一天起就用同一套工程骨架，只把中间「融合」这一步做成输入输出契约一致的适配器。**

修正后的架构（详见 05 号文档 §6）：

```
[输入] 用户照片 + 角色三视图（白底）+ 用户标注框
  S0 预处理     BiRefNet 抠像 → RGBA → 形态学腐蚀去白边（确定性，无模型）
  S1 几何感知   Depth Anything V2-Small 估深度 → 拟合框底边的地面平面
                → 建议缩放系数 + 遮挡候选区
  S2 融合生成   适配器 A：Qwen-Image-Edit-2511 自托管（Apache-2.0）
                适配器 B：Qwen-Image-Edit API（同模型）
                适配器 C：Seedream 4.0 API（闭源，仅作效果上限对照）
  S3 接触阴影   GPSDiffusion，仅在 QC 判定「悬浮」时触发
  S4 生成后 QC  白边检测 / mask与框IoU / HarmonyScore / OPAScore → 排序
  S5 输出       按分数排序的候选 + 每张的失败标签
```

三个关键取舍：

1. **几何遵从必须靠工程件硬保障。** 用户拖了框就是要她站在那里，靠提示词只能提高概率。所以 S1 和 S4 的 IoU 校验不是可选项。
2. **「宁可不出阴影，也不要出方向错的阴影」。** 错的接触阴影用户一眼看出假；没阴影只是"有点飘"，仍有一半可用率。S3 因此设计成条件触发而非必经。
3. **评分模型可用，合成模型不可用。** libcom 的 OPA / Harmony / FOS 是纯判别模型，不依赖 Flux Kontext，可安全商用——正好是最有产品价值的那部分。这是原版这一节唯一被保留的判断。

## 4. 许可协议风险表（已按 05 / 06 号文档修正）

> 本节原版有三个阻断级错误，已全部修正。规则改为一句：**任何一个开源件进入商业产品前，许可以「仓库 LICENSE + 权重 LICENSE + 默认流程里所有自动下载的第三方模型 LICENSE」三者取交集为准。只看仓库 LICENSE 会漏掉下面全部三个坑。**

**先记一条能省掉后续全部麻烦的团队规则**：

> **凡是 FLUX 家族，先一律当不可商用。** 整个 FLUX 家族里只有 `FLUX.1-schnell` 是 Apache-2.0，而**它只能文生图，没有编辑能力**；所有编辑变体（dev、kontext、pro）一律非商用。这条规则让我们不必再逐个去查——需要"编辑"就一定不能用 FLUX。

> 唯一注意：不要因为这条规则否掉 `libcom` 全部——它的**判别式评分模块**（OPA / Harmony / FOS）不碰任何生成权重，可以安全商用。

> **补充一条容易踩的坑**：不要试图在 FLUX 家族里找"可商用的 Kontext 平替"。按 flux 仓库 README 模型表，Apache-2.0 的只有 `FLUX.1 [schnell]`（**纯文生图**）；所有具备编辑能力的变体——`[dev]`、`Fill [dev]`、`Canny [dev]`、`Depth [dev]`、`Redux [dev]`、`Kontext [dev]`、`Krea [dev]`——**全部是 FLUX.1-dev Non-Commercial License**。也就是说：**FLUX 的"可编辑"能力整体锁在非商用许可里。** 商用编辑路线只能用 Qwen-Image-Edit 这类 Apache-2.0 权重，这不是偏好问题，是唯一选项。

## 5. 对需求侧的启示

### 5.1 计费方式要改

emoji 小人的差评里明确提到"换个风格就得再付一次，试两张钱包已经开始疼了"。**建议按次计费（一次 = 一组 4 张候选），而不是按张计费。** 因为我们的产品里"一张合格"才是交付物，"4 张中间挑一张"是过程。

### 5.2 位置标注可以更聪明

FOPA 这类模型能给出"哪里适合放人"的热力图。产品上可以做成：用户拖框 → 框位置打分 → 低分时实时提示。**这比"生成完发现不对再重来"省一次 1.2 元的成本**，也省用户一次等待。

### 5.3 抠图边缘发白是已发生的公开问题

emoji 小人用户明确抱怨"抠图边缘偶尔还会露白"。我们的设定图是纯白底，风险更高。**预处理必须去白底，且生成后要做边缘检测**。

### 5.4 "生成两三分钟"是竞品的实际表现

emoji 小人用户说"生成一张差不多等了两三分钟"。我们预估 60 秒内，这是明确优势，应该在产品里把这个感知做出来（不是显示假进度条，而是明确告诉用户"约 40 秒"）。

## 7. 下一步建议（第三次重排，以 06 号文档为准）

> **本节被改过两次，现在是第三版。**
> 第一版：libcom 工作台先行（错，那个模块非商用）。
> 第二版：GPSDiffusion 判生死（这是 05 号文档的结论）。
> **第三版（当前）**：06 号文档把接触阴影改为**程序化渲染**后，GPSDiffusion 从"主路径"降为"对照方案"，不再是生死项。
> **新的生死项是 S2——Qwen-Image-Edit-2511 在三视图 + 二次元 + 写实照片这个输入下的框位遵从率与角色漂移率。**

| 新顺序 | 动作 | 成本 | 判什么 |
|--------|------|------|--------|
| **1（新生死门）** | **Qwen-2511 双形态对照**：API 与自托管，同一批 30 张照片跑同一组提示词 | 1 天 + API 费约 100 至 200 元 | 框位遵从率（角色 mask 与用户框的 IoU）、角色漂移率、单张成本。**这三项决定产品核心承诺是否成立** |
| **2（ROI 最高）** | 实现 S3 三项程序化后处理：重力对齐旋转 / 深度匹配散焦 / 接触阴影三层渲染 | 2 天，纯 CPU | 不依赖 GPU、不依赖模型效果、不等任何人。做完立刻拿到"返修率从 35% 降到多少"的第一个硬数据 |
| 3 | 写 S4 八项 QC 打分卡 | 2 天 | 打分与人工观感的相关性。若相关性低，自动排序不成立 |
| 4 | GPSDiffusion 做对照实验 | 半天，0 元 | 程序化阴影 vs 模型阴影，谁在非平面地面（草地/台阶/斜坡）更好 |
| 5 | BiRefNet 抠三张白底设定图，检查白边 | 0 元 | 白底残留是竞品已发生的公开问题，必须先解决 |
| 6 | 扩到 30 张 × 三类场景测可用率 | 200 至 300 元 | 决定 MVP 开放哪些场景 |

**第 2 步值得单独强调**：它是当前唯一"不需要等任何人、不需要花钱、两天能做完、且做完就有硬数据"的事。如果只能做一件事，做这个。

### 7.1 GPSDiffusion 对照实验的验收标准（保留，但降级为对照项）

原第二版把它当生死门时定的标准仍然有效，只是现在用来判断"要不要用模型阴影替代程序化阴影"：

- 每场景独立评，**不混算平均**
- 每场景 30 张里至少 **21 张（70%）** 可用
- 方向错（阴影轴向与主光方向夹角 **> 5 度**）**一票否决**
- 阴影面积占角色占地 **< 15%**

### 7.2 一句话记住

~~先证伪阴影，再验证融合~~ → **先证伪融合（S2），再补程序化几何（S3），阴影降为对照。**

理由：程序化阴影的失败模式是**可预期**的（复杂地面、软体轮廓），而且能靠"降级为只有 AO 层"兜住；而 S2 的框位遵从率是**不可预期**的，它一旦不达标，整个产品承诺就没了。

**宁可不出阴影，也不要出方向错的阴影** 这条原则不变，只是实现从"模型或不出"变成"程序化或只出 AO 层"。
