## 0. 结论先行

**一、路线裁决：走混合路线，但混合的方式和 03 号文档写的不一样。**

不是「阶段 1 纯 API → 阶段 3 自建开源栈」的线性递进，而是**从第一天起就用同一套工程骨架，只把中间的「融合」这一步做成可替换的适配器**。原因很硬：Qwen-Image-Edit-2511 的权重是 Apache-2.0 且可下载，API 与自建跑的是同一个模型。把 API 和自建当两条路线，等于为同一个模型写两套代码。正确的切法是「骨架固定 + 生成器可插拔」。

**二、03 号文档的核心结论成立，但有三处必须修正（其中两处是法律风险）。**

libcom 确实是这个领域的工具箱，模块清单逐条核实无误。但 03 号文档把它标成「Apache 2.0 可商用」是**不完整的**——libcom 里最对口的那个模块 `KontextBlendingHarmonizationModel` 底下挂的是 Flux Kontext，而 Flux Kontext 的权重是**非商用许可**。Apache-2.0 的代码许可不能覆盖非商用的模型权重。这是本项目目前最大的一个隐形法律坑。

**三、You asked 的两个具体问题，直接回答。**

- **AnyDoor 能用吗**：能跑，权重能下，MIT 许可，但**不进原型主线**。理由不是"停更"，是「基座代差 + 跨域失败」：它基于 2023 年的 SD 2.1，训练数据以真实物体为主，我们喂的是二次元角色设定图，属于训练分布外。它的价值在交互范式（框内传送）和论文思路。
- **IC-Light 能把前景光照改成匹配背景吗**：能。`iclight_sd15_fbc.safetensors` 就是背景条件重打光模型，输入前景图 + 背景图，输出光照匹配的前景。但它同样是 SD1.5 基座、512 分辨率，对二次元角色质量折损明显，且默认流水线用 BRIA RMBG-1.4（非商用）。判定：可作对照实验，不作主路径。

**四、`Anime_In_Real_Life` 和 `QWEN-AI-Compositing` 两个「可直接抄的骨架」，法律上都不能抄。**

两个仓库**都没有 LICENSE 文件**。03 号文档把后者标成 MIT，是错的（GitHub 许可字段为空，根目录只有 workflow JSON + README）。无许可证 = 默认保留所有权利。可以读，不能复制代码。

## 1. 核实方法与判定标准

判定「直接可用」的四条硬门槛，缺一条降级为「仅可借鉴」：

| 门槛 | 判据 |
|------|------|
| 有许可且可商用 | 仓库 LICENSE 明确为 MIT / Apache-2.0 / ISC / BSD，**且权重许可逐层穿透到基座模型** |
| 未死 | 最近提交在 18 个月内（即 2025-04 之后） |
| 有权重 | 提供可下载的预训练权重，不是只有论文代码 |
| 输入匹配 | 能接受「二次元角色图 + 真实照片」这种跨域输入，或至少有明确的可微调路径 |

只要「输入匹配」这条塌了，前三条全过也只能做借鉴——因为我们的场景是跨域，而绝大多数图像合成模型的训练分布是「真实物体 + 真实场景」。

逐条说明：

**AnyDoor**：交互范式与本项目几乎完全一致——在场景图上指定位置，把参考图的物体传过去，自动调整姿态、角度、光照并生成阴影反射。权重在 ModelScope 与 HuggingFace 均有（`damo/AnyDoor`、`xichenhku/AnyDoor`）。作者自述的两大局限直接影响我们：一是依赖用户标注的 mask，「过粗的 mask 会影响生成质量」；二是没有针对特定品类做优化，官方明确说虚拟试衣场景「不包含专门设计」，建议在专有数据上微调。二次元角色属于更远的域外输入，微调成本不比直接换基座低。**原型阶段不投入。**

**Paint-by-Example**：CreativeML OpenRAIL-M 不是标准 OSI 许可，它允许商用但附带使用限制条款（禁止违法、禁止生成特定有害内容等），且要求下游分发时传递同样限制。对我们这种 To C 产品，属于「能用但要法务过一遍」。技术上是 SD1.4 时代的工作，单次前向，思路清晰（信息瓶颈 + 强增强防退化），但现在有更好的替代。**仅借鉴它的「信息瓶颈防复制粘贴」思路。**

**InsertDiffusion**：这篇的价值在于**训练免费**（training-free），直接复用现有扩散模型的先验，不需要训练新权重。它的「image mode」正好是「把白底物品渲染进任意背景」。但 22 星、2024-08 后无提交、无社区验证，工程风险高。**仅借鉴思路。**

**DreamComposer（重要澄清）**：03 号文档未收录，team-lead 的清单里把它归到「把参考物体放进场景」。核实结果：CVPR 2024 的 DreamComposer 是**从多视角条件生成 3D 物体**（`yhyang-myron/DreamComposer`），另一篇同名工作做的是人体外观渲染。**没有一篇是「把参考物体插入照片」**。这条是名字混淆，从选型清单里剔除。

**ObjectDrop**：核实结果是**没有官方代码仓库**。GitHub 上仅有项目页（5 星）。它真正的贡献是「用物体移除模型自动合成遮挡训练数据」的方法论，对我们有启发（用前置步骤制造训练配对），但一行代码都拿不到。**只能读论文。**

### 2.2 重打光类

| 项目 | 仓库 | Star | 最近提交 | 许可 | 解决哪一环 | 判定 |
|------|------|------|----------|------|-----------|------|
| IC-Light | lllyasviel/IC-Light | 8,561 | 2025-02-20 | Apache-2.0（代码） | 打光 | 可直接用（有约束） |
| ComfyUI-IC-Light | kijai/ComfyUI-IC-Light | 1,162 | 2025-05-30 | Apache-2.0 | 打光（节点封装） | 可直接用 |
| comfyui-relight | EnragedAntelope/comfyui-relight | 110 | 2026-10-10 | MIT | 打光（可摆放光源） | 可直接用（需实测） |
| Diff-Harmonization | WindVChen/Diff-Harmonization | 151 | 2025-11-25 | Apache-2.0 | 光照协调（零样本） | 可直接用（对照） |

**IC-Light 的能力边界要说清楚**：它解决的是「给定前景和背景，重新打光让前景光照匹配背景」，不解决「生成接触阴影」，也不解决「位置摆放」。三个权重文件的分工是——`iclight_sd15_fc`（文本+前景条件）、`iclight_sd15_fcon`（加 offset noise，用户研究里略差）、`iclight_sd15_fbc`（文本+前景+**背景**条件，这个才是我们要的）。它的「Imposing Consistent Light」技巧让重打光结果能直接合并出法线图，这意味着它输出的光照是物理自洽的，不是画上去的——这一点对「写实光影」的要求很关键。

**两个必须知道的约束**：
1. 默认流水线用 BRIA RMBG-1.4 抠图，该模型**非商用**。README 明确写了：商用项目必须换成 BiRefNet 等替代品。
2. SD1.5 基座 + 512 分辨率。二次元角色在这个分辨率下细节会糊，且 SD1.5 对二次元与写实的混排天然不擅长。做对照实验可以，做主路径不行。

`comfyui-relight` 是本次核实里唯一一个 2026 年还在积极更新的重打光件（110 星，MIT，2026-10-10），描述是「不重新生成图像，支持最多 3 个可摆放光源、颜色」。方向对，但星数太少、无可查证的效果评估，**列为原型阶段的 B 方案（A 方案见第 6 节）。**

| 项目 | 仓库 | Star | 最近提交 | 许可 | 解决哪一环 | 判定 |
|------|------|------|----------|------|-----------|------|
| GPSDiffusion | bcmi/GPSDiffusion-Object-Shadow-Generation | 153 | 2026-08-20 | MIT | 接触阴影（CVPR 2025） | 可直接用 |
| DESOBAv2 + SGDiffusion | bcmi/Object-Shadow-Generation-Dataset-DESOBAv2 | 163 | 2026-08-20 | Apache-2.0 | 接触阴影（CVPR 2024） | 可直接用 |
| DESOBA 数据集 | bcmi/Object-Shadow-Generation-Dataset-DESOBA | 173 | 2026-08-20 | **MIT**（03 号文档误记为 Apache） | 训练数据（AAAI 2022） | 可直接用 |
| ARShadowGAN（官方实现） | ldq9526/ARShadowGAN | 69 | **2020-03-10** | **无许可证** | 接触阴影（经典基线） | 仅可借鉴 |
| ARShadowGAN-like 复现 | Everypixel/arshadowgan-like | 31 | 2020-12-15 | MIT | 接触阴影（PyTorch 复现） | 仅可借鉴 |

**这是本次核实里质量最高的一组。** 三个仓库同属上交 BCMI 团队，2026-08 仍在维护，构成「数据集 + 方法 + 改进版」的完整链条：

- **DESOBA**：21,575 张真实图像、28,573 组物体-阴影对，全为户外真实场景。这是目前唯一大规模的真实物体阴影配对数据集。
- **DESOBAv2 + SGDiffusion**（CVPR 2024）：基于扩散模型的阴影生成，输入是合成图 + 前景 mask，输出带阴影的图。
- **GPSDiffusion**（CVPR 2025）：加了几何先验的改进版，官方说明是「带几何先验的扩散阴影生成」。已被 libcom 收录为 `ShadowGenerationModel`。

**对我们的适配性风险（必须实测）**：DESOBA 系列全部在**户外真实场景**上训练（README 原文 "from outdoor scenes"）。我们的输入是室内外混合的真实照片 + 二次元角色，属于双重域外。它大概能处理「物体在地面上的投影」这种常规情形，但二次元角色的半透明裙摆、飘带、非刚体轮廓是否会被正确处理，需要实测才知道。**这是原型阶段第一优先的实测项。**

**ARShadowGAN 一系可以直接排除**：官方实现 2020 年停更、**无许可证**（法律上不可用）、基于旧版 PyTorch 环境难配。03 号文档写的「环境难配」是对的，但漏了「无许可证」这个更硬的问题。

**Depth Anything V2 有个必须写进采买清单的分级许可**：仓库层面 Apache-2.0，但 README 明确分级——`Small` 权重 Apache-2.0，`Base / Large / Giant` 权重 **CC-BY-NC-4.0（非商用）**。也就是说商用只能用小模型。好消息是 Small 只有 24.8M 参数、精度在多数场景够用（用于判断地面平面和粗略遮挡关系）。**这一条 03 号文档漏了，必须补进许可风险表。**

**GroundingDINO 已停更**（2024-08），但它是 Apache-2.0 且有广泛的下游集成，做「用文本定位地面/桌面/椅子」这类辅助任务仍可用。不过我们的场景里用户已经手动标了框，深度和分割只需要处理「框内区域」，GroundingDINO 的边际价值不高。**建议不进 MVP 依赖，留作后续「自动推荐落点」的组件。**

**SAM 2 vs BiRefNet 的分工**：SAM 2 做「指定区域分割」（用户点一下框内，得到角色精确轮廓，用于遮挡判断和阴影投射 mask）；BiRefNet 做「整图抠像」（处理白底设定图的前景提取）。两者不是替代关系，都要。

**Qwen-Image-Edit 是本次调研里唯一一个「许可、能力、活跃度」三项全过的生成式模型，这是路线裁决的核心依据。**

核实到的事实：
- 仓库许可 Apache-2.0，README 第 582 行「License Agreement」明确 "Qwen-Image is licensed under Apache 2.0"，权重与代码均开放，可商用。
- 官方 README 首屏直接给出 Edit 权重链接 `Qwen/Qwen-Image-Edit-2511`（当前版本），2509 为上一版。
- 2511 相对 2509 的关键改进：减少图像漂移、单人/多人角色一致性提升、**内置社区热门 LoRA（含光照控制）** 不再需要外挂、最多支持 3 张参考图输入。
- 官方与社区文档中反复出现的示例指令就是「把图 1 里的人放到图 2 的厨房里，站在台面旁，自然的窗光从左边照进来」——**与本项目的任务形式逐字对应。**

这条彻底改变成本模型：既然权重 Apache-2.0 可直接下载，且模型原生支持「主体图 + 场景图 + 光向描述」三要素，那么「自建」不再是遥不可及的事。但它同时意味着「既然 API 和自建跑同一个模型，就不要写两套代码」（见第 6 节）。

**FLUX.1 Kontext [dev] 的许可必须写死**：`black-forest-labs/flux` 仓库 README 的模型表明确列出 Kontext [dev] 为 "FLUX.1-dev Non-Commercial License"。商用需向 BFL 单独购买授权。**这直接导致 libcom 的 `KontextBlendingHarmonizationModel` 在商业产品里不可用**（详见第 3 节）。

**Step1X-Edit 是干净的备选**：Apache-2.0（README 第 443 行明确），2026-04 发布 Step Image Edit 2（主打 2 秒内完成编辑的轻量版），有官方 FP8 量化权重。它的定位是「对标闭源编辑模型」，评测表里直接和 Flux-Kontext-dev 对比。若 Qwen 路线在某类场景上不达标，它是第一顺位替换。

**Qwen-Image-Layered 值得留意**：2025-12 发布，把图像分解成独立 RGBA 图层。对我们的潜在用法是——生成合成图后，把角色层与背景层拆开，独立做调色和阴影叠加，避免整图重绘导致角色细节丢失。**列为 MVP 后优化项，不进第一版。**

**生态里没有现成的「二次元角色插入实景 + 接触阴影」一体化节点包。** 有的是零件：Qwen-Image-Edit 的编辑节点（ComfyUI 已原生支持，官方还提供了一批含重打光的工作流模板）、IC-Light 节点、深度/分割节点。要把它们串成我们的流水线，串接逻辑得自己写。这一点必须写进排期——不是「装个节点包就完事」。

**`ComfyUI-RealProductScene` 虽然只有 3 星，但它的架构判断值得抄**：生成「空的场景背景」→ 把真实产品 PNG 按原比例合成进去 → 处理接地与光影，且明确写出「产品像素 100% 来自原图，AI 不重画产品，只负责周围场景、接地与光影」。这正是「保真优先」的正确取舍——**我们的角色设定图比产品图更需要保真，这个思路应当沿用：能贴就别让模型重画。**

**ComfyUI 的 GPL-3.0 要分清场景**：作为**内部推理服务**使用（SaaS 后端调用，不向用户分发 ComfyUI 本身）不受 GPL 传染；但如果未来做「本地部署版客户端」把 ComfyUI 打包进去分发，就要遵守 GPL-3.0 的开源义务。**MVP 阶段按内部服务定位，风险为零，但排期里要留一句备注。**

### 2.7 前端框选与合成

| 库 | 仓库 | Star | 最近提交 | 许可 | 适用性 |
|----|------|------|----------|------|--------|
| fabric.js | fabricjs/fabric.js | 31,520 | 2026-10-22 | MIT | **推荐** |
| cropperjs | fengyuanchen/cropperjs | 13,912 | 2026-10-16 | MIT | 不适用 |
| react-image-crop | dominictobias/react-image-crop | 4,109 | 2026-06-21 | ISC | 不适用（仅裁剪） |

**三者的差别不是「谁更好」，是「解决的是不是同一个问题」**：

- `cropperjs` 和 `react-image-crop` 解决的是**裁剪**——框是「要保留哪一块」，鼠标拖动的是裁剪窗口，输出是一张新图片。**我们要的不是这个**，我们要的是「在原图上标一个位置框，框本身是给模型的输入，原图不变」。
- `fabric.js` 解决的是**画布图层**——给你的是可拖拽、可缩放、可旋转、可带把手（handle）的对象层，坐标是画布坐标，事件、边界约束、键盘微调、命中检测全部现成。这正是「用户拖一个框、框有 8 个缩放手柄、框不能拖出画面」这套交互需要的东西。

**对 03 号文档 §2.8 的一处不同意见**：该文档写「原型阶段我们手写 Pointer Events 即可，不引 fabric.js」。这个判断在「只有单个不可旋转的矩形」时成立（约 150 行代码）。但产品一旦加上「框可旋转」「框内再放一个角色缩略图层」「多候选切换时框要跟随」，手写成本会快速超过引入成本，且容易在移动端触摸事件上踩坑（手势冲突、缩放误触）。**建议：若 MVP 确认只需要「单个不可旋转矩形 + 双指缩放画布」，手写 Pointer Events 是对的（少 200KB 依赖）；一旦需求出现旋转或图层，直接上 fabric.js，不要中途自己造。这个决策点应该在交互稿定稿时锁死，不要留到开发中途。**

## 3. 三个许可链路陷阱（本次核实最重要的发现）

### 3.1 libcom 的 Apache-2.0 不能覆盖它内部的 Flux Kontext 模块

libcom 仓库本体 Apache-2.0，这是真的。但它 README 第 66 行明确：

> `KontextBlendingHarmonizationModel` [[FluxKontext]] is a generative image composition model which inserts foreground into the specified bounding box in the background... The "harmonization" mode adjusts the foreground illumination to make the composite image harmonious.

而 Flux Kontext 的权重许可是 **FLUX.1-dev Non-Commercial License**（`black-forest-labs/flux` README 模型表第 47 行）。

**结论：libcom 的调用代码可以商用，但它调起来的那个权重不能商用。** 商用必须换成有商用许可的同功能模型——也就是 Qwen-Image-Edit。这意味着 03 号文档第 3 层架构图里的「Qwen-Image-Edit-2511 + Fusion LoRA 框内合成」不只是「更好」，是**唯一合规的选择**。

`OSInsertModel` 同属这一组（同为「框内插入」），且 `bcmi/OSInsert-Image-Composition` 仓库**未检测到 LICENSE 文件**，其基座模型许可也未在仓库层面声明。**双重待核实，不得使用。**

### 3.2 三个「可直接抄骨架」的仓库，两个没有许可证

| 仓库 | LICENSE 文件 | 03 号文档说法 | 事实 | 法律含义 |
|------|-------------|--------------|------|----------|
| haoyang504/Anime_In_Real_Life | **无** | 「需再确认」 | 根目录 18 个文件，无 LICENSE | 默认保留所有权利，**代码不可复制** |
| rik-python/QWEN-AI-Compositing | **无** | 「MIT」 | 根目录仅 4 项，无 LICENSE | 同上，**代码不可复制** |
| bcmi/libcom | 有，Apache-2.0 | Apache-2.0 | 一致 | 可商用（但见 3.1） |

两个仓库可以读、可以照着思路自己写，但不能复制文件。特别是 `QWEN-AI-Compositing`——它那一个 workflow JSON 里如果能看出「背景/主体/遮罩/阴影区」四个输入的接法，这个信息本身有价值（思路不受版权保护，代码受），但直接拿 JSON 来用不行。

### 3.3 权重许可必须穿透，不能只看仓库

本次核实挖出的三处分级/例外：

| 组件 | 仓库许可 | 实际权重许可 | 后果 |
|------|----------|-------------|------|
| Depth Anything V2 | Apache-2.0 | Small=Apache-2.0；Base/Large/Giant=**CC-BY-NC-4.0** | 商用只能用 Small |
| FLUX.1 Kontext [dev] | Apache-2.0（代码） | **非商用** | 需要 BFL 商业授权 |
| IC-Light | Apache-2.0 | 模型权重随仓库发布；但默认流程依赖 **BRIA RMBG-1.4（非商用）** | 商用必须换 BiRefNet |

**采买/法务清单的规则写成一句：任何一个开源件进入商业产品前，许可以「仓库 LICENSE + 权重 LICENSE + 默认流程里所有自动下载的第三方模型 LICENSE」三者取交集为准。** 只看仓库 LICENSE 会漏掉上面三个全部。

## 6. 推荐架构：单一骨架 + 可插拔生成器

### 6.1 数据流

```
[输入]  用户照片  +  角色三视图（白底）  +  用户标注框 (x, y, w, h)
   |
   |-- S0 预处理（确定性，无模型）
   |    照片：EXIF 旋转归一、长边限制 2048、生成缩略图
   |    设定图：BiRefNet 抠像 -> RGBA -> 去白边（形态学腐蚀 1-2px）
   |
   |-- S1 几何感知（轻量模型，可缓存）
   |    Depth Anything V2-Small 估计照片深度 -> 拟合用户框底边的地面平面
   |    -> 输出建议缩放系数（角色高度 / 画面高度）
   |    -> 输出遮挡候选区（框内深度值小于地面平面的像素 = 应被遮挡）
   |
   |-- S2 融合生成（可插拔适配器）
   |    Adapter-A: Qwen-Image-Edit-2511（自托管，Apache-2.0）
   |    Adapter-B: Qwen-Image-Edit API（同模型，外部服务）
   |    Adapter-C: Seedream 4.0 API（闭源，仅做效果上限对照）
   |    统一输入：{场景图, 角色RGBA, 框坐标, 光向描述, 场景描述}
   |    统一输出：N 张候选（N=4）
   |
   |-- S3 接触阴影补强（仅当 S2 输出被 QC 判定"悬浮"时触发）
   |    GPSDiffusion(合成图, 角色mask) -> 带阴影结果
   |    或 Qwen-Image-Edit 局部 mask 重绘（仅重绘框底边下方 15% 条带）
   |
   |-- S4 生成后 QC（判别式，全部可商用）
   |    边缘白边检测 | 角色mask与框的IoU | HarmonyScore 光影和谐 | OPAScore 位置合理
   |    -> 打分排序，低分候选标注失败原因（供 A/B 分析，不展示给用户）
   |
   |-- S5 输出：按分数排序的 4 张 + 每张的失败标签
```

### 6.2 为什么这是「混合」而不是「两阶段递进」

关键在 S2 的适配器化。三个 Adapter 的**输入输出契约完全一致**，切换只改配置：

| 考虑 | 若做成「阶段 1 API / 阶段 3 自建」 | 做成「单一骨架 + 适配器」 |
|------|-----------------------------------|---------------------------|
| 代码量 | 两套调用逻辑、两套重试、两套计费 | 一套，Adapter 内各自实现 |
| 提示词工程资产 | API 阶段的提示词在自建时可能失效（模型版本不同） | 同模型同提示词，资产可迁移 |
| 效果对照 | 跨阶段对照，中间隔了几周，变量不可控 | 同一天同一批图 A/B，变量可控 |
| 切换成本 | 需要一次改造 | 改一个枚举值 |
| 计费验证 | 阶段 1 能算清单次成本 | 同样能算清，且能与自建实时比价 |

**这条建议的实际含义**：原型第一周就同时接 Adapter-A 和 Adapter-B/C，用同一批 30 张照片跑对照。这样「自建还是买 API」这个问题在第 1 周就有数据，而不是等到「有量之后」再拍脑袋。

### 6.3 每环节的失败兜底

| 环节 | 失败模式 | 兜底 |
|------|----------|------|
| S0 抠像 | 白底残留、边缘白边 | 形态学腐蚀 + 边缘 alpha 羽化；QC 检出白边则拒绝该候选 |
| S1 深度 | 二义性场景（镜面、玻璃、纯色墙面）估错平面 | 深度置信度低时降级为「仅用框底边做尺度」，不做遮挡 |
| S2 融合 | 角色被重画导致形象漂移 | 用 S4 的 FOSScore + 人工抽检监控；漂移率超阈值则切「贴图 + 局部重绘」模式（能贴就别重画） |
| S2 融合 | 不遵从框位（生成在别处） | QC 比对角色 mask 与框的 IoU，低于阈值直接判失败并重试一次，不进入排序 |
| S3 阴影 | 阴影方向与照片光向矛盾 | 从深度图估计主光向，阴影方向做一致性检查；不一致则回退「不生成阴影」而非生成错阴影 |
| 全链路 | 4 张全失败 | 明确告知用户可以调整框位置重试（这一条要写进 PRD 的失败态交互） |

**「宁可不出阴影，也不要出方向错的阴影」是这里的核心取舍。** 错的接触阴影比没有阴影更破坏真实感——用户会立刻看出「这张是假的」，而没有阴影只是「有点飘」，仍有约一半的可用率。

### 6.4 路线对比评分（回答 team-lead 的最终问题）

三个候选路线，按本项目权重打分（1-5 分，5 最好）：

| 维度 | 权重 | 纯开源工程合成<br>（AnyDoor+DESOBA+IC-Light 堆叠） | 纯商业 API<br>（Seedream / Qwen API） | **混合（本报告推荐）** |
|------|------|------|------|------|
| 许可干净 | 高 | 3（AnyDoor MIT 可用，但 ARShadowGAN 无证、Kontext 非商用） | 4（闭源，商用条款需法务确认，无侵权风险但有依赖风险） | **5**（全链 Apache-2.0 / MIT，逐层核实） |
| 首版出图速度 | 高 | 1（4-5 个模型串联，环境与权重配齐需 2-3 周） | 5（1 天跑通） | **4**（1 周，因为要接骨架） |
| 效果上限 | 高 | 2（基座是 2023-2024 年产物，二次元跨域） | 4（Seedream 4.0 强，但不可控不可微调） | **4**（Qwen-2511 同代，且可微调） |
| 几何可控性 | 高 | 4（框位可由算法硬约束） | 2（生成式不保证框位，易漂移） | **4**（框进参数 + QC 拒绝重试） |
| 边际成本 | 中 | 5（趋近电费） | 3（0.2 元/张，量大可观） | **5**（切自建即趋近电费） |
| 二次元适配 | 高 | 2（训练分布外） | 4（2511 官方主打角色一致性） | **4**（同 2511，可 LoRA 微调） |
| 运维复杂度 | 中 | 2（多模型多环境） | 5（无） | **3**（自建段需 GPU） |
| 可迭代性 | 高 | 3（改一个环节要动全链） | 2（只能调提示词） | **5**（适配器 + QC 标签驱动迭代） |
| **加权合计** | | **2.5** | **3.4** | **4.3** |

**最终结论：走混合路线。骨架 = 确定性工程件（框 + 深度 + 分割 + 掩码 + QC 评分），唯一生成器 = Qwen-Image-Edit-2511（Apache-2.0 权重，先用 API 形态接，第一周即建立自托管对照）。**

三条理由，按分量排：

1. **纯开源工程路线的问题不是「不够好」，是「代差」**。这条路线里最核心的两个生成件——AnyDoor 和 Paint-by-Example——分别停在 2024-04 和 2023-11，基座是 SD2.1 和 SD1.4。而 Qwen-Image-Edit-2511 是 2025-12 的 20B MMDiT，原生支持 3 张参考图与内置光照 LoRA。用 2023 年的模型去做 2026 年的产品，等于主动放弃三年半的模型进步。**我们没有理由为了「开源自建」这个形式，去用差三年的模型。**

2. **纯商业 API 路线的硬伤是几何遵从，而几何遵从是本产品的核心承诺**。用户拖了个框，就是要角色站在那里。生成式模型的输出位置由模型决定，靠提示词只能提高概率。S4 的 QC 拒绝重试能兜一部分，但每次重试都是成本与延迟。**必须有工程件在框这一层做硬保障**，这就是混合的由来——不是折中，是两边的强项各自补对方的短板。

3. **混合路线在许可上是唯一全干净的**。纯开源工程路线必然会踩到 ARShadowGAN（无许可证）和 Flux Kontext（非商用）之类的坑，而且这些坑分散在链路的深处，发现时往往已经写了很多代码。混合路线把所有生成压力收敛到 Qwen-Image-Edit-2511 这一个 Apache-2.0 的模型上，外围全是 MIT/Apache-2.0 的判别与小模型，许可审查只需过一遍。

## 8. 架构侧的两个附带约束

## 9. 下一步（技术侧，按优先级）

| 顺序 | 动作 | 成本 | 产出 | 为什么排这个位置 |
|------|------|------|------|------------------|
| 1 | 跑 GPSDiffusion，输入 = 手工合成的「照片 + 二次元角色」5 组 | 半天 + 1 张 GPU | 判断接触阴影这一步能不能用开源件解决 | 这是本项目技术难度最高、且唯一没有生成式替代方案的一环；先判生死 |
| 2 | 接 Qwen-Image-Edit-2511 API 与自托管，同一批 30 张跑对照 | 1 天 + API 费用 | 框位遵从率、光影和谐度、单张成本三条曲线 | 这一步同时回答「走 API 还是自建」，越早越好 |
| 3 | 写 S4 QC 四个检测器（白边、mask IoU、光影、位置） | 2 天 | 自动排序能力 + 失败标签 | 有了它才能量化上面两步的结果，否则全靠肉眼 |
| 4 | 接 libcom 的三个评分模型，用第 1、2 步产出的图做一致性验证 | 1 天 | 确认评分与人工观感是否一致 | 若不一致，自动排序的价值要重估 |
| 5 | 再决定要不要动 AnyDoor / IC-Light 做对照 | — | — | 前四步的数据如果已经够用，这两个都不必碰 |

**注意第 1 步和第 2 步的顺序不能换。** 阴影是唯一没有「生成式模型顺手做了」的环节，也是最可能让整条路线报废的环节。如果 GPSDiffusion 对二次元角色的阴影生成完全不可用，那么路线要重新评估——可能得接受「无阴影 + 靠 QC 拦住悬浮感」的降级方案，这个决策必须在写代码之前做。
