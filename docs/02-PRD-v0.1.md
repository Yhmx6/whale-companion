## 1. 产品定义

**一句话**：上传一张自己的照片，把Q版鲸鱼娘「放」进去——位置合理、光影贴合，看起来她真的就站在那里。

**目标用户**：二次元内容消费者，尤其是 DeepSeek / 鲸鱼娘形象的爱好者、日常喜欢给自己照片加元素的年轻用户。

**核心问题**：现有的 AI 出图工具让用户"生成一张新图"，而用户真正想要的是"我的照片里多一个人"。这是两种完全不同的心理诉求——前者要的是想象力，后者要的是**陪伴感与在场感**。"她出现在了我的生活里"这句话，是这个产品的全部价值。

**产品价值主张**：不是生成图片，是生成"她来过"的证据。

## 2. 目标用户与使用场景

### 2.1 用户画像

| 画像 | 特征 | 核心诉求 |
|------|------|----------|
| 主画像：二次元日常分享者 | 18 至 28 岁，手机相册里全是生活照，习惯在社交平台发图配文 | 我拍的照片不够特别，需要一点"惊喜感" |
| 次画像：角色粉丝 | 对鲸鱼娘形象有情感连接 | 想要角色出现在自己的生活场景里，而不是看官方立绘 |

### 2.2 典型场景

| 场景 | 用户动作 | 期望结果 |
|------|----------|----------|
| 旅行打卡 | 站在景区路边拍了一张 | 她站在我旁边跟我一起打招呼 |
| 咖啡店 | 拍了一张空椅子和对面的杯子 | 她坐在对面看着我 |
| 家里桌面 | 拍了书桌 | 她趴在桌角探出头 |
| 公园长椅 | 拍了一张空长椅 | 她坐在长椅上晃腿 |

### 2.3 不服务的场景（原型阶段）

- 多人合照（需要处理多人遮挡与相对位置，复杂度陡增）
- 极暗环境、强逆光、雨雪雾
- ~~大幅俯拍与大幅仰拍~~ **【用户已确认放宽】**：改为**仅排除俯仰角超过 30 度的极端情况，以及无可见地面的场景**
  - 依据：重力对齐落地后（地面平面法线法，S1 本来就要拟合地面），5 至 15 度轻微倾斜（手持随意拍、坐台阶拍，占相册比例很大）都可服务
  - 前提：桌面特写、仰拍只见天空这类无地面场景，重力估计降级或置零——对应产品决策见 §9「趴姿默认只出接触暗区」
- 需要角色与照片中人物发生肢体互动（握手、拥抱）

## 3. MVP 范围

### 3.1 P0（原型必须做）

| 编号 | 功能 | 说明 |
|------|------|------|
| F-01 | 照片上传 | 支持相册选择与拖拽；自动压缩到长边 2048；拒绝超大图与非法格式 |
| F-02 | 位置标注 | 用户在照片上拖出一个矩形框，表示角色大致占据的区域 |
| F-03 | 接触面选择 | 标注后从四个选项里选一个：地面 / 椅子 / 桌面 / 墙面。这是提升"坐倚"类场景成功率的关键字段 |
| F-04 | 场景理解 | 后端调用视觉模型，输出主光方向、色温倾向、相机俯仰角、场景类型 |
| F-05 | 生成候选 | 一次生成 4 至 6 张候选，带进度反馈 |
| F-06 | 结果挑选与下载 | 网格展示候选，点击查看大图，可下载 |
| F-07 | AI 标识 | 生成图上叠加"AI生成"标识，导出文件保留 |
| F-08 | 生成记录 | 本地记录每次生成的参数与结果，用于统计成功率 |

### 3.2 P1（原型后补，不做会可惜）

| 编号 | 功能 | 说明 |
|------|------|------|
| F-09 | 姿势模板 | 站立 / 倚靠 / 坐 / 趴，由**接触面 + 框宽高比确定性推导预选**（地面+瘦高框→站；椅子+方框→坐；桌面+扁宽框→趴；墙面+瘦高框→倚靠），用户可改，不做独立必填步骤 |
| F-10 | 精修开关 | 对已出结果做二次光影精修（对应方案的 L2） |
| F-11 | 位置微调重生成 | 用户在已出图上拖动角色位置，只重生成局部 |
| F-12 | 下载尺寸选择 | 提供社交平台常用的方图与竖图裁切 |

### 3.3 明确不做（锁定，防止范围蔓延）

| 不做的功能 | 原因 | 何时考虑 |
|------------|------|----------|
| 三种形态切换 | 形态越多，一致性校验组合越多，测试量翻倍；Q版成功率最高，先跑通 | MVP 上线且Q版成功率达标后 |
| 用户自建/训练角色 | 需要训练链路、审核链路、存储成本，与"验证核心体验"无关 | 有明确付费需求后 |
| 多人合照 | 遮挡与相对位置推理难度陡增 | 不做 |
| 分享裂变与社区 | 原型阶段无账号体系，且公开传播会触发内容审核义务 | 小程序阶段 |
| 视频动图输出 | 视频一键成片的成本与失败率远高于图片 | 图片链路稳定后 |
| 手动精细抠图/图层编辑 | 目标用户不接受专业工具式交互 | 不做 |

## 4. 交互流程

### 4.1 主流程（四步）

1. **传图** — 拖入或选择一张照片，主体画面立刻铺满
2. **标位** — 在照片上拖出一个框，框底边落在地面或接触面上；框的大小决定角色身高。松手后框内浮现半透明剪影示意，让用户直观看出"她大概这么大、站这里"
3. **选接触面 + 姿势** — 四个接触面选项中选一（地面/椅子/桌面/墙面），姿势可选"随机"
4. **出图** — 一次出 4 至 6 张候选，网格排列；点击看大图，满意可下载；不满意可"再生成一组"

### 4.2 关键交互决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 标注粒度 | 粗框，不要求精确到像素 | 用户不会标，也标不准；框只是给模型一个"大致在这儿、大概这么大"的强约束 |
| 是否让用户看生成过程 | 只给阶段文案（理解场景 → 正在生成 → 精修中），不显示百分比 | 生成耗时不均，假进度条会引发更强的等待焦虑 |
| 候选数量 | 4 至 6 张 | 写实融合单张成功率不高，必须靠数量兜住；但超过 6 张会带来"选择困难"和成本上升 |
| 失败处理 | 全部候选都不合格时，引导用户"把框往画面中间挪一点"或"换一个接触面" | 失败归因要给出可操作建议，而不是"生成失败请重试" |

### 4.3 异常路径

| 情况 | 处理 |
|------|------|
| 标注框超出画面或过小 | 限制框高在画面高度的 15% 至 85%，框宽同理；超限时框自动吸附到合法范围 |
| 照片中人物占比极大（如自拍大头） | 提示"这张照片里没有足够的空位，换一张全身或半身的试试" |
| 生成超时（> 90 秒） | 显示"还在处理，可以稍等或重试"；后台任务继续，完成后可回到记录页查看 |
| 模型返回内容被安全审核拦截 | 提示"这张照片无法处理，请换一张"，不暴露具体拦截原因 |
| 全部候选质量很差 | 记录到实验数据，提示用户调整框位置或接触面后重试 |

## 5. 验收标准（EARS 格式）

> 这些标准同时是 Step 1 实验的打分依据，也是原型开发完成后的验收依据。

### 5.1 功能类

| 编号 | EARS 验收标准 | 优先级 |
|------|---------------|--------|
| AC-01 | When 用户拖入一张 JPG/PNG 且长边不超过 8000 像素的照片，系统**必须**在 3 秒内完成压缩并展示预览 | P0 |
| AC-02 | If 用户上传 HEIC 或超过 20MB 的文件，系统**必须**给出明确的格式或体积提示，而不是静默失败 | P0 |
| AC-03 | When 用户在照片上拖拽，系统**必须**实时绘制矩形框并在松手后显示框内剪影示意 | P0 |
| AC-04 | If 用户拖出的框高小于画面高度的 15% 或大于 85%，系统**必须**自动吸附到最近的合法尺寸 | P0 |
| AC-05 | When 用户未选择接触面就点击生成，系统**必须**阻止提交并高亮接触面选项 | P0 |
| AC-06 | When 用户点击生成，系统**必须**在 90 秒内返回至少 1 张候选图，否则给出超时提示 | P0 |
| AC-07 | When 生成完成，系统**必须**一次展示 4 至 6 张候选，且每张都可点开查看原尺寸 | P0 |
| AC-08 | When 用户下载结果图，导出文件中**必须**包含可见的"AI生成"字样标识 | P0 |
| AC-09 | When 每次生成结束，系统**必须**把照片尺寸、框坐标、接触面、模型名、耗时、候选数写入本地数据表 | P0 |
| AC-10 | While 用户在一次会话内已生成 10 次，系统**必须**提示额度用尽并阻止继续（原型阶段防止成本失控） | P1 |

### 5.2 质量类（核心）

| 编号 | EARS 验收标准 | 优先级 |
|------|---------------|--------|
| AC-11 | When 生成完成，系统**必须**对每张候选执行**角色门禁检测**（鲸尾连通域存在 + 藏青色占比在区间内，结构化输出到"哪个特征失分"；门禁阈值与排序阈值分离，取 precision ≥ 0.9 的高精度点，宁可漏检不要误触发——门禁假阳性是一次完整往返的延迟与成本，而延迟打穿 AC-06 比角色画歪更致命）。检测不过的候选触发补救或降权，**不得静默当作正常候选展示**；两个特征同时失分说明问题在生成质量而非参考配置，重跑无意义，直接降权 | P0 |
| AC-12 | While 结果为"可用"，角色与接触面**必须**贴合，且**按姿势模板分别判定**（不能统一按站姿判，否则坐/倚/趴永远无法通过验收）：<br>- **站立**：双脚落在接触面上，身体竖直轴与照片重力方向夹角 < 1.5°<br>- **坐姿**：臀部与椅面接触，大腿前伸方向与椅面透视一致<br>- **倚靠**：身体轴允许与重力成 10 至 20°夹角（本就不平行），但接触侧（肩/背/臀）必须贴住支撑物<br>- **趴姿**：身体轴近水平，胸口/手臂与桌面接触，探出部分自然下垂 | P0 |
| AC-13 | While 结果为"可用"，角色**必须**与原照片主光方向一致，且脚下或身侧有可见的接触阴影（按 §9 姿势规则：趴姿与置信度不足时允许只出 AO 接触暗区） | P0 |
| AC-14 | While 结果为"可用"，角色**不得**出现明显的肢体畸变、多余肢体、穿模或背景残留白边 | P0 |
| AC-15 | When 同一张照片连续生成两次，两次结果的发色与裙装主色**应该**保持一致（允许姿势不同） | P1 |
| AC-19 | When 生成任何候选，**输出图宽高比必须与用户原照片一致**（实现层约束：生成管线取**最后一张输入图**的尺寸作为输出比例，因此必须显式传 height/width 按原照片等比锁定，同时把场景照片置于输入序列末位作第二道保险） | P0 |

### 5.3 体验类

| 编号 | EARS 验收标准 | 优先级 |
|------|---------------|--------|
| AC-16 | While 生成进行中，界面**必须**显示当前阶段文案，用户可离开页面且结果不丢失 | P0 |
| AC-17 | When 全部候选均不合格，系统**必须**给出至少一条具体可操作的建议（调整框位置 / 更换接触面） | P0 |
| AC-18 | While 在手机浏览器访问，标注框**必须**支持单指拖拽与双指缩放 | P1 |

## 6. 非功能需求

| 类别 | 要求 |
|------|------|
| 性能 | 上传压缩 < 3s；单次生成端到端 P90 < 60s；候选图并发请求而非串行 |
| 兼容 | Chrome / Safari / Edge 最近两个大版本；移动端 Safari 与微信内置浏览器可用 |
| 响应式 | 断点 768px 与 1200px；手机端标注区域占满屏宽 |
| 可观测 | 每次生成记录耗时、模型、成功/失败、候选数，用于统计成功率 |
| 安全 | 模型 API Key 只在后端；上传文件校验 MIME 与真实文件头；生成结果文件名随机化 |
| 隐私 | 照片与生成结果仅本地存储，原型阶段不上传第三方存储；提供"删除本次记录" |
| 成本 | 单次生成成本上限 2.5 元；单会话上限 10 次 |

## 7. 合规要求

原型阶段不做公开运营，但流水线必须预留以下节点，避免后期改造：

| 要求 | 原型阶段做法 | 小程序阶段做法 |
|------|--------------|----------------|
| 显式标识 | 生成图上叠加"AI生成"字样 | 同，并把样式规范化 |
| 隐式标识 | 预留写入 EXIF/XMP 的函数位 | 写入属性信息、服务提供者名称或编码、内容编号 |
| 类目资质 | 不需要 | 申请 `深度合成-AI绘画` |
| 内容安全 | 依赖模型侧审核 | 增加独立的内容安全审核调用 |
| 用户协议 | 不需要 | 明确标识方法与样式，提示用户标识义务 |

**参考事实**：2026 年 9 月国家网信办通报，四川某科技公司运营的微信小程序因 AI 图片生成未加显式与隐式标识，被依法责令下线。标识不是可选项。

## 8. 数据表（原型阶段）

### 8.1 generations 表

| 字段 | 类型 | 说明 |
|------|------|------|
| id | TEXT | 主键，随机 UUID |
| created_at | TEXT | ISO 时间 |
| photo_path | TEXT | 原始照片本地路径 |
| photo_w / photo_h | INTEGER | 压缩后尺寸 |
| box_x / box_y / box_w / box_h | REAL | 归一化到 0 至 1 的标注框 |
| contact_surface | TEXT | ground / chair / desk / wall |
| pose_template | TEXT | 姿势模板，或 random |
| scene_json | TEXT | VLM 输出的结构化场景描述 |
| model_name | TEXT | 使用的生成模型 |
| candidate_count | INTEGER | 候选数量 |
| latency_ms | INTEGER | 端到端耗时 |
| picked_index | INTEGER | 用户最终选择了第几张（未选为 null） |
| picked_available | INTEGER | 用户标注该结果是否可用（0/1），实验核心字段 |

### 8.2 关键指标

| 指标 | 定义 | 原型目标 |
|------|------|----------|
| 单张可用率 | picked_available=1 的数量 / 总生成张数 | 待 Step 1 测定基线 |
| 单次成功率 | 一次生成中至少一张可用 | ≥ 60% |
| 首次选中率 | 用户在第一组候选里就选中某张 | ≥ 70% |
| 二次生成率 | 用户点"再生成一组"的比例 | 越低越好，反映质量 |
| 平均耗时 | 端到端 | < 60s |

## 9. 产品决策记录

| 日期 | 决策 | 原因 | 影响 |
|------|------|------|------|
| 2026-10-26 | 融合风格选"光影融合写实"而非贴纸风 | 用户明确选择，价值上限更高 | 单张成功率下降，必须多候选；技术方案需 L2 精修兜底 |
| 2026-10-26 | 摆放方式为"用户预标 + 系统随机"双轨 | 用户明确选择 | 需前端框选交互 + 后端几何换算；不做纯自动布局 |
| 2026-10-26 | 先做 Web 原型而非小程序 | 用户明确选择 | 省去资质、类目、备案；但后端 API 契约须按小程序标准设计 |
| 2026-10-26 | 只做Q版 | 用户明确选择 | 一致性校验从 3 形态收敛到 1 形态；参考图裁切坑需处理 |
| 2026-10-26 | 后端用 Fastify 而非 Next.js 单体 | 前端未来会换成小程序，后端须与前端框架解耦 | 多一个进程，但迁移成本最低 |
| 2026-10-26 | 计费按「次」不按「张」（一次 = 一组 4 至 6 张候选） | 竞品 emoji 小人的真实差评：「换个风格就得再付一次，试两张钱包已经开始疼了」。而本产品的交付物是"一张合格"，4 张中间挑一张是过程 | 付费墙体验更可接受；单次成本 1.2 元需靠额度控制 |
| 2026-10-26 | 角色库策略锁定：不新增角色，只增加场景与姿势 | hololy（hololive 官方 AR 合影，3D 模型、角色一致性最强、IP 最强）仍于 2024-12-02 停服，死因是角色供给速度追不上用户消耗速度。妙鸭相机 2025-09 团队解散，死因是"一年用一次的窄场景" | 资源投入方向从"做新角色"转为"做新场景/新姿势"；用户相册每天更新，"出场机会"天然高频 |
| 2026-10-26 | 产品定位明确写入"虚构角色，可大方发圈" | 海外最贴近的竞品 YouCam Perfect「推し活加工」自己在新闻稿里写「因可能引起误解，请勿发布到社交平台」。同类产品都卡在"我发这张图会不会被觉得怪" | 结果图需预留可配文的边距，让"发出去"成为产品的一部分 |
| 2026-10-26 | 原型阶段严格限定"只生成照片，不做持续情感互动" | 《人工智能拟人化互动服务管理暂行办法》2026-07-15 施行，适用范围是"模拟自然人人格特征、思维模式和沟通风格的**持续性的情感互动服务**"；法条明确排队智能客服、知识问答、工作助手等不涉持续性情感互动的服务 | 一旦加入对话或人设互动，即落入适用范围，需补未成年人模式、防沉迷提醒、安全评估与算法备案。此边界在原型阶段写死 |

## 10. 产品定位与商业结构（竞品调研后增补）

### 10.1 定位一句话（对外叙事）

> **不是"生成一张有她的图"，是"她今天陪你去过这里"。**

三类同类产品各自卡在不同的坎上：陪伴类做对了角色一致但放弃了写实融合；写真/换脸类把用户的照片整张重绘；AR 类靠 3D 模型硬贴、全靠用户手动摆。

**我们的空档是：不改用户的照片，只往里加一个人，且这个人有影子。**

### 10.2 一条内部保留的差异，不进对外文案

**【用户已确认：对外叙事只讲陪伴感，不强调虚构角色属性】**

有一条事实值得内部记住：海外最贴近的竞品 YouCam Perfect「推し活加工」，自己在新闻稿里写「因可能引起误解，请勿发布到社交平台」。它做出了功能，却劝用户别传播——说明整个品类都卡在"我发这张图，别人会觉得我怪吗"这个心理问题上。

鲸鱼娘是明确虚构的角色，天然规避了真人肖像的风险（Meta Muse Image 因抓取真人肖像 3 天下线）与"她真的存在"这种欺骗性叙事。**这层安全性继续作为内部合规与选型依据保留**：

- 绝不把真人肖像作为生成素材（规避 Meta 死法）
- 角色形象与人设无暧昧指向（规避筑梦岛被约谈的死法）
- 结果图仍预留可配文的边距，让"发出去"顺畅

但**对外文案不主打"虚构所以可以大方发"**。用户选择了只讲陪伴感——叙事落在"她今天陪你去过这里"，而不是落在对角色的元讨论上。讲虚构属性反而会把用户引向"这是假的"这个认知框架，与陪伴感叙事相冲。

### 10.3 反面教材划出的三条硬边界

| 教材 | 结局 | 对我们的约束 |
|------|------|--------------|
| Meta Muse Image | 2026-07-07 上线，**3 天紧急下线**。@一个 Instagram 账号即可把真人拉进生成图，被 Public Citizen 称"对用户隐私的肆意侵犯"，CAA 抗议 | **绝不把真人肖像作为生成素材**。我们只插入虚构角色 |
| hololy（hololive 官方 AR 合影） | 2024-12-02 停服。3D 模型、角色一致性最强、IP 最强、粉丝最忠诚，仍然死了。玩家诉求是"出个离线版，不用更新衣服就够" | **不靠加新角色续命**，靠加新场景与姿势 |
| 妙鸭相机 | 2025-09 团队解散；安卓 246 万安装、评分 2.5、好评率 36%；典型差评"拍了一次就没再打开过，不值" | **不做"一年用一次"的窄场景**。她的出场机会必须由用户每天的相册驱动 |

### 10.4 北极星指标

| 指标 | 为什么是它 | 健康值 |
|------|-----------|--------|
| **周均生成次数 / 人** | 妙鸭死于低频，hololy 死于供给跟不上消耗。这个指标同时验证"场景是否高频"和"内容供给是否够" | 待内测测定 |
| **首轮命中率** | 第一组候选里就有用户愿意保存的图。反映质量，也直接决定成本 | ≥ 70% |
| **二次生成率** | 双刃指标：过高说明质量不行；过低且首轮命中率高才是健康 | 观察趋势 |
| 单次生成成本 | 免费额度模型下的生死线 | ≤ 2.5 元 |

### 10.5 三条不可降级的质量红线

竞品与行业复盘显示，写实合成失败集中在五处，其中三处必须列为不可降级的验收项：

1. **接触阴影**（最致命）——脚底没有压紧的暗部，人像"悬空五公分"。这一圈是"重量感"的唯一来源，缺了大脑立刻报警，直接产生 floating sticker 效果
2. **统一光源**——人物光与环境光不能是分别生成的。模型没有"光源"概念时，会出现"脸完全受光但身侧有方向性阴影"的物理矛盾
3. **透视匹配**——业内实测口径：一百张里八十张的假感来自肩线胯线角度差 1 至 2 度

另两处（阴影软硬不分层、机械连接穿帮如镜框缺鼻托）作为 P1 观察项。

**参考数据**：一键合成返修率 35% 以上，手动分层合成返修率约 8%。这个差距就是我们产品的存在理由——把 8 分钟的手工活变成 4 步点击。
