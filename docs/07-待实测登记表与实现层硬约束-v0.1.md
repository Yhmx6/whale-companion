## 1. 实现层硬约束（H 系列，已核实，写代码前必须知道）

以下六条是架构师 r1/r3 轮核实源码后确认的**硬事实**，不是猜测。全部有源码行号或双源文档支撑。

| 编号 | 约束 | 依据 | 对方案的直接后果 |
|------|------|------|------------------|
| **H-1** | Qwen-Image-Edit 输入图**总数上限 3 张，含基底/场景图**。阿里云百炼文档「支持传入 1-3 张图像」；WaveSpeed 2511 文档「maximum 3 total，the first image is typically the main base image」 | 双源文档一致 | **角色参考图只有 2 张额度**（原以为 3 张）。分工：正面（主身份锚）+ 侧面（鲸尾立体形态——正面物理上不可见的信息）。第三张为条件触发 |
| **H-2** | **输出宽高比取自输入列表最后一张图**。diffusers `pipeline_qwenimage_edit_plus.py` 第 645 行：`image_size = image[-1].size`；与阿里文档「输出图像比例以最后一张为准」对上 | 源码 + 官方文档 | 按 `[场景, 正面, 侧面]` 顺序传，输出比例会跟侧面图（多为 3:4 竖幅）走，**用户照片被裁切或拉伸——上线首日就暴露的 bug**。对策双保险：①显式传 `height`/`width` 按原照片 1024² 面积等比换算；②场景照片置于输入序列**末位** |
| **H-3** | **每张参考图进编码器前被压到约 384² 面积**。同源码第 66-67 行：`CONDITION_IMAGE_SIZE = 384*384`，`VAE_IMAGE_SIZE = 1024*1024` | 源码 | 一张全身三视图板进 384² 后单角色有效宽度仅约 128px；紧裁单视角约 384px，**细节清晰度差 3 倍**。→ S0 必须「一个视角一张、紧裁到角色外接框 + 小幅留边」，**禁止整板直喂**。这也是**否决拼图方案的决定性理由**：两视角拼一张，每个角色有效宽度掉到约 192px，省 1 个额度换细节减半 + 高概率版式失败 |
| **H-4** | **diffusers 管线显式拒绝批处理**：`if batch_size > 1: raise ValueError("...only supports batch_size=1...")` | 源码 | 双配置候选（2 张保鲸尾 + 2 张保纹样）在托管 API 下约单次往返（服务端并发）；**自托管单卡下是串行、约两倍延迟**。→ **自建门槛从一张卡变两张**（V-23/U-23），这个数字足以翻转自建 vs API 的成本结论 |
| **H-5** | **「3 张」是训练分布与托管 API 的限制，不是代码限制**。开源权重走 diffusers 时管线对 `image` 列表长度**无断言无上限**，只是把每张图的 latent 沿序列维拼接（源码第 491 行 `torch.cat(all_image_latents, dim=1)`） | 源码 | 自托管**理论上可传更多图**。若实测 4 张（3 角色参考 + 场景）质量更好，自建就多了一条**能力理由**而不只是成本理由——这可能是自建唯一能拿到 API 拿不到的东西。注意序列变长后注意力开销超线性增长，测质量须同步记延迟 |
| **H-6** | **GPSDiffusion 的输入格式 = `shadowfree_imgs`（已贴物体但无阴影的合成图）+ `object_masks`，输出 `shadow_imgs`**——恰好就是 S2 输出的东西（我们让 2511「不要生成地面阴影」，产出的正是无阴影合成图） | 源码 `tutorial_dataset.py` | 接口层面完全兼容，**不需要写适配层**（05 号报告此处结论已修正）。域外风险只在训练数据分布，不在格式 |

**一条方法论（全团队适用）**：二手文档描述与源码行为不一致时，**以源码为准**。证据优先级：README < 官方 API 文档 < 源码。阿里文档写「支持 1-3 张」读起来像能力描述，实际是数组长度限制；真正决定成败的两条（H-2、H-3）藏在源码里，文档一字未提。
