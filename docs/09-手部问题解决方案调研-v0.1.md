# 手部问题解决方案调研 v0.1

> 日期：2026-10-26
> 问题：贴贴动作里"手该抓住却没抓住"（扯衣角、抱手臂、牵手指）
> 方法：GitHub / 论文检索 + 1 次真实调用实测
> 结论先行：**有一条立刻可用的低成本路径，不需要 ControlNet 也不需要 GPU**

---

## 一、先分清两层问题，它们的解法完全不同

| 层 | 症状 | 典型解法 | 我们遇到的是哪层 |
|----|------|----------|------------------|
| **L1 解剖** | 六指、手指融合、关节反折 | HandRefiner 这类"修手"工具 | 不是 |
| **L2 接触关系** | 手的位置对，但没有真正抓住物体；该贴的地方没贴上 | 需要姿态/接触条件控制 | **是** |

这个区分不是学术洁癖，有硬数据支撑。GraspDiffusion（WACV 2026）在 DexYCB 上的对比：

| 方法 | hand-contact 成功率 |
|------|---------------------|
| **GraspDiffusion** | **97.94%** |
| Affordance Diffusion | 65.69% |
| **HandRefiner** | **61.45%** |

**HandRefiner 是修 L1 的顶级工具，但它解决 L2 的能力只有 61%。** 我们一直在为 L2 头疼，所以"用 HandRefiner 修手"这个直觉是错的——它修的是手指数量，不是抓握关系。

## 二、检索到的五条路线与可行性判定

| 方案 | 出处 | 解决 L1 | 解决 L2 | 对我们的可行性 |
|------|------|---------|---------|----------------|
| **HandRefiner** | `wenquanlu/HandRefiner`，ACM MM 2024 | 强 | 弱（61.45%） | **不可用**，理由双重 |
| **GraspDiffusion** | WACV 2026，`yj7082126/graspdiffusion` | 强 | **最强**（97.94%） | **不可用**，输入不匹配 |
| **Affordance Diffusion** | 论文 | 中 | 好（contact recall 87%） | 只借鉴思路 |
| **Qwen-Image-Edit-2509 + ControlNet pose** | `QwenLM/Qwen-Image`，原生支持 depth/canny/**pose** | 强 | 强（实测 4/4 正确举手） | **自建可行**，需 GPU |
| **Seedream 坐标定位编辑** | 方舟官方能力（本次实测） | 中 | **有效** | **立刻可用，+0.12 元/次** |

### 2.1 HandRefiner 为什么对我们不适用（两个独立理由）

它的原理是：MediaPipe 检测手 → MeshGraphormer 重建 3D 手 mesh → 转 depth 图 → ControlNet inpainting 重绘手部。

**理由一（官方 FAQ 原文）**：
> 「这些模型没有在卡通或动漫图像上训练过，所以 mesh 重建阶段有**很大概率失败**」

我们的角色是 Q 版动漫，正好落在它的盲区。

**理由二**：它只修解剖结构，不改手与物体的关系。就算 mesh 重建成功，手还是没抓住衣角。

另外两个限制也卡我们：手至少 60×60 px；它不放大手。

### 2.2 GraspDiffusion 为什么不能直接用

它的输入是**3D 物体 mesh + 相对位置**，输出是"一个人抓住这个物体"的全身图。我们是"往已有照片里插一个 2D 角色"，输入形态根本不匹配，而且它是研究代码、无产品化接口。

**但它的一个洞察值得抄**：论文明确指出，只告诉模型"在这里生成交互"不够，必须**用 negative mask 显式告诉交叉注意力"不要在这里生成"**，否则会出现悬浮物体和幽灵肢体。这解释了为什么我们的否定式提示词（"不要多余的手指"）效果差——**否定要走注意力掩码，不走文本**。

### 2.3 Affordance Diffusion 的可借鉴之处

它把问题拆成两步：**LayoutNet 决定"手放哪"（2D 位置/大小/朝向），ContentNet 只负责"手长什么样"**。

这个拆分对我们有直接启发：**手的位置应该由程序/骨架决定，模型只填内容**。落地形式就是路线 2.4 的 ControlNet 关键点，或者更轻的坐标框。

### 2.4 Qwen-Image-Edit-2509 + ControlNet pose（自建路线）

- Qwen-Image-Edit-2509 起**原生支持 ControlNet 条件输入**：depth / canny / **pose** / scribble，不需要外挂插件
- DWPose 可选 `body` / **`hand`** / `face` 关键点
- 有实测记录：只用 Qwen-Image-Edit 让"人物举起右手"，4 张里 2 张对、1 张举错手、1 张没举；**加上 OpenPose ControlNet 后 4 张全对**

这是唯一能真正"钉住手位"的产品化技术路线。代价：需要 GPU、要搭 ComfyUI、20B 模型。**属于自建阶段才做的事**，不是现在。

### 2.5 Seedream 坐标定位编辑（本次实测有效）

Seedream 5.0（Pro 与 Flash **同一套能力**）支持在提示词里用归一化坐标（0-999）指定编辑区域：

```
Replace the area Image 1 120 180 640 760 with ...
keep Image 1 700 120 920 360 unchanged
```

**实测**：拿第 4 批"扯衣角"的失败图（手没捏住下摆），用差分掩码算出角色区域 `[353, 354, 999, 810]`，发一次编辑指令要求"同一角色、但手牢牢捏住衣角、布料捏出三角形褶皱，其余区域不变"。

结果（`output/step6/compare_handfix.jpg`）：

| 项 | 结果 |
|----|------|
| 手是否抓住 | **是**，手到了下摆边缘，布料出现被拉出的褶皱 |
| 区域约束是否生效 | **是**，人物、发丝、背景树木完全一致，没有整图重绘 |
| 副作用 | 角色本身被轻微重绘（脸型、姿态略有变化），需要靠措辞约束 |
| 成本 | 1 次调用 = 0.12 元（Flash）/ 0.30 元（Pro） |

**这是当前最划算的修手方式**：不需要 mask 参数、不需要换模型、不需要 GPU、不需要新依赖。

## 三、推荐的三层策略

| 层 | 做法 | 成本 | 状态 |
|----|------|------|------|
| **第一层：设计上绕过** | 只放"手天然处于遮挡位"的动作（坐肩膀、扒肩探头、趴肩后）；"手必然暴露在空处还要抓握"的动作直接不做 | 0 | **已落地** |
| **第二层：坐标定位重绘** | 出图后对手部区域做一次局部重绘，指令写"手捏住 X、布料被拉出褶皱" | +0.12 元/次 | **已实测有效**，待接入流水线 |
| **第三层：ControlNet 钉手位** | 自建 Qwen-Image-Edit-2509 + DWPose hand 关键点，把手的位置作为硬条件 | GPU 成本 | 自建阶段再做 |

**三层是递进关系，不是替代关系。** 第一层决定"哪些动作能上产品"，第二层兜住"上了但要修的那部分"，第三层是彻底解。

---

## 四、接入第二层时要注意的三件事

1. **手部区域要精准，不能用角色整体框。** 本次实测的框是 `[353,354,999,810]`，x1 到了 999——说明差分掩码把人物的衣服也算进去了。正式实现应该用 MediaPipe Hands 或 DWPose 手部关键点定位，或者让用户点一下手的位置。

2. **坐标重绘会轻微改动角色本身。** 本次结果里脸型和姿态都有变化。要在指令里加重"保持角色的发型、耳朵、服装、大小、位置完全不变，只改手"，并在之后跑一遍 `defringe` + `match_ambient` 收尾。

3. **确认坐标语法在方舟直连也成立。** 本次实测说明**它成立**（HTTP 200 且区域约束明显生效），但第三方文档与官方文档的表述不完全一致，正式接入前建议用 2 到 3 个不同区域各测一次，确认边界行为。

## 五、明确排除的方案

| 方案 | 排除原因 |
|------|----------|
| HandRefiner | mesh 模型对动漫手大概率失败 + 只修解剖不修接触（61.45%） |
| ARShadowGAN 类旧 GAN | 与手无关，且无许可证 |
| 靠否定式提示词 | 已有两处证据（禁白边、禁手指）证明"不要 X"在这类模型上遵从度低；GraspDiffusion 也从机理上解释了原因——否定要走注意力掩码而非文本 |
| 直接换 Gemini 3 Pro Image | 交互能力更强，但境内合规与网络都不可用 |

## 七、追记：用户指出"浮空了，动作也不匹配"——其中一半是我的代码 bug

### 7.1 浮空：确认是流水线错误，已修

**根因**：我在 companion 模式里一律关掉了地面阴影，把它当成"挂在人身上"的动作。但 `pull_hem`（扯衣角）、`pull_trouser`、`hug_calf`、`hug_thigh`、`hand_hold` 都是**站在地上**的——它们需要脚落地和地面阴影。

**我漏了一个维度：支撑方式。** 动作库原来只有"难度档位"，没有区分"她靠什么承重"：

| support | 含义 | 动作 | 阴影处理 |
|---------|------|------|----------|
| `person` | 挂在人身上 | 坐肩膀、扒肩、趴肩后、坐头顶、抱手臂、坐腿上、贴脸、从口袋探出 | 影子落在人物衣服上，由模型负责 |
| `ground` | 站在地上 | 扯衣角、扯裤脚、抱小腿、抱大腿、牵手 | **必须程序化画地面阴影，否则浮空** |

已加入 `Action.support` 字段，并在 `pipeline` 里按它分派。

**修复过程中又踩一个坑**：第一次修完仍然报 `ground_skip`（没画出影子）。原因是取掩码的时机在**后处理之后**——`defringe` 会把轮廓亮边填成角色内部颜色、`match_ambient` 会把角色色偏往背景拉，两者都削弱了与原图的差分，导致掩码检测失败。
改为用**未后处理的 raw** 取掩码，并加了一层兜底（掩码失败时退回用户框）。修完后 `shadow=ground_ao`，脚下有阴影了。

### 7.2 动作不匹配：这是真问题，不是 bug

修完落地后，她的手到了衣摆，但**身体没有"往后拽"的姿态**——没有后倾、手臂没有伸直、布料没有绷紧。这个改不了：

- 已在 `desc` 里显式写了"身体微微向后倾，一只手向前伸直手臂拉住……布料被拉得绷紧、拉出一个三角形的褶皱"，模型仍未表达
- 原因是 Q 版角色四肢极短，"后倾 + 伸直手臂"这个身体语言在 2.5 头身的比例下几乎没有表达空间
- 属于 L2 接触关系问题（见本文第一节），只能靠第三层（ControlNet 钉手位）彻底解

**结论：`pull_hem` / `pull_trouser` 维持 C 档，不放进产品。** 修复浮空只是让它"不那么假"，没有让它"能用"。

### 7.3 这次事故的两条经验

1. **"贴贴"不是一种模式，是两类动作。** 悬挂类和站立类的接触面、阴影、承重逻辑完全不同，用一个布尔开关（companion）去覆盖所有动作，必然在其中一类上出错。数据结构要能表达这个差异。
2. **后处理会破坏用于后处理判断的信息。** 差分掩码依赖"角色与背景的差异"，而 `match_ambient` 的职责恰恰是减小这个差异。**凡是需要掩码的步骤，掩码必须在所有颜色类后处理之前算好并缓存。**
